# tests 타입 검사(P3)·미사용 명령 제거(B9)·실제 SSH 회귀

- 실행일: 2026-11-06 / 대상: `0a9286f` + P3·B9 미커밋 변경 / 환경: Windows 11, Docker 28.5.1 Linux 엔진
- CI는 `-Native` 없이 실행하므로 아래 네이티브 결과는 전부 로컬 결과다.

## 변경

- P3: `tsconfig.tests.json`을 추가하고 `npm run typecheck`에 연결했다. Windows·macOS 게이트 모두 이 스크립트를 쓴다. 기록된 6건 외에 `assistant.config.ts`의 `node:url` 타입 오류 1건을 `cwd: '..'`로 해결했다.
- `@types/node`는 설치하지 않았다. 이 때문에 `process`를 쓰는 루트 `playwright.config.ts`와 `scripts/`는 타입 검사 대상이 아니다.
- B9: `config_import`, `transfer_cancel`, `transfer_resume`, `transfer_drop`을 `lib.rs`, `build.rs`, `capabilities/main.json`에서 제거했다.
- 빌드는 고아 권한 파일을 지우지 않으므로 `permissions/autogenerated/`의 해당 toml 4개를 직접 삭제했다. 삭제 후 `build.rs` 명령과 toml이 77개로 일치한다.
- `test-native.mjs`, `test-ftp-native.mjs`의 업로드는 제품의 드롭 경로인 `transfer_batch`(`mode: 'drop'`)로 바꿨다. 이전 `transfer_drop`은 legacy 큐 경로를 탔으므로 UI 네이티브 검사가 쓰는 전송 경로가 달라졌다. legacy 경로(`Transfers::start`)는 `transfer_pick`이 계속 쓰며 실증 예제가 검사한다.
- `test-native.mjs` 실패 출력에 스택의 파일·줄 번호를 모두 남기게 했다. 오류 메시지는 계속 가린다.

## 판단과 한계

- 실패한 두 단계는 같은 EXE로 코드 변경 없이 통과했다. B9는 금고와 터미널 코드를 건드리지 않았다. 따라서 실패 원인이 이번 변경이나 특정 기능의 고장이라는 근거는 없고, 검사가 불안정하다고 본다.
- **근본 원인은 확인하지 못했다.** 1회차는 출력 필터로 실패 줄을 잃었고, 2회차는 줄 번호 151(`output` 헬퍼)만 남아 어느 호출인지 모른다. 줄 번호를 모두 남기는 수정 후에는 실패가 재현되지 않았다.
- 실행 당시 여유 RAM이 약 2~3GiB였고 다른 에이전트가 같은 PC에서 동작 중이었다. 부하와의 관련은 추정이며 측정하지 않았다.
- 1회의 전체 통과로 회귀 없음이 증명되지는 않는다. 실패율은 표본 3회로 판단할 수 없어 T5로 남긴다.
- 실제 PodTree, Mac, 물리 IME는 이번 범위에서 실행하지 않았다.

## 환경 메모
