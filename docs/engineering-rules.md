# DachsTerm 구현 규칙

Codex와 Claude Code가 함께 따르는 규칙이다. 범위·디자인·보안 기준은 [roadmap](roadmap.md), 진행 상태는 [progress](progress.md)가 정본이고, 이 문서는 코드를 어떻게 쓰고 검증을 어떻게 보고하는지를 정한다.

**기존 코드 적용 방식**: 새 코드와 수정하는 부분에 적용한다. 기존 위반을 고치려고 관련 없는 파일을 함께 바꾸지 않는다. 구조 정리는 [architecture-review](architecture-review.md)의 ID 단위로 별도 작업한다.

표시: `[자동]`은 현재 게이트가 강제한다. 표시가 없으면 작성자와 리뷰어가 지킨다.

## 1. 공유 작업 트리

- 작업 전 `git status`를 확인하고, 내가 만들지 않은 변경은 수정·복원·스테이징하지 않는다.
- 다른 에이전트가 같은 트리에서 작업 중이면 일괄 포맷, 줄바꿈 정규화, 파일 이동, 대규모 리팩터를 하지 않는다.
- 커밋은 사용자가 요청할 때만 하고, 내 변경 파일만 경로로 지정해 스테이징한다.
- 소스 사본이나 worktree를 `target/` 아래에 만들지 않는다. 테스트 필터에 함께 잡히고, 제거할 때 공유 산출물이 지워질 수 있다.

## 2. 검증 보고

- 숫자는 실행한 명령의 출력에서 옮긴다. 테스트 수가 이전 기록과 크게 다르면 원인을 먼저 확인한다.
- "통과"에는 명령, 범위, 대상 커밋 또는 미커밋 여부를 함께 적는다.
- 푸시한 작업은 `gh run list`로 CI 결과를 확인해 기록한다. 로컬 통과를 CI 통과로 적지 않는다.
- 실패한 게이트를 두고 후속 기능을 쌓지 않는다. 진행해야 한다면 실패 내용과 이유를 progress 상단에 남긴다.
- 현재 소스로 재실행하지 않은 결과를 "현재 상태"로 적지 않는다.

## 3. 문서

- `docs/progress.md` 상단에는 현재 상태, 남은 작업 ID, 다음 첫 행동만 둔다. 상태가 바뀌면 이전 문장을 고치고, 새 문단을 위에 쌓지 않는다.
- 작업 시작 시 progress는 상단과 상태 표, 해당 작업 ID의 섹션만 읽으면 된다.
- 상세 검증은 `docs/verification/`에 두고 progress에는 링크와 결론만 적는다.
- "커밋 요청", "푸시 완료"처럼 git 이력으로 알 수 있는 내용은 기록하지 않는다.
- README는 사용자와 개발자가 쓰는 방법만 적고, 작업 ID별 경과를 넣지 않는다.

## 4. 공통 구조

- 같은 로직을 두 번째로 복사하게 되면 공용화를 먼저 검토한다. 세 번째 복사는 하지 않는다.
- 비슷해 보여도 정책이 다르면 합치지 않는다. 분리를 유지하는 이유를 주석으로 남긴다.
- 파일은 작업 Phase가 아니라 기능 이름으로 짓는다(`test-phase63-67-native.mjs` 같은 이름 금지).
- 제품 코드가 호출하지 않는 명령과 함수를 남기지 않는다. 테스트 전용 코드는 테스트 영역에 둔다.
- 파일 크기 상한은 TS/TSX 400줄, Rust 600줄이다(테스트 제외, 게임 엔진 포함). 넘으면 분리한다.
- 아래 파일은 이미 상한을 넘었으므로 **순증 없이** 수정한다. 새 기능은 새 파일로 분리한다.
  - `App.tsx`, `FilePanel.tsx`, `TunnelPanel.tsx`
  - `transfer_queue.rs`, `session_transfer.rs`, `ssh.rs`, `session_log.rs`, `podtree.rs`, `ftp.rs`
  - `SurvivorGame.tsx`, `AdventureGame.tsx`, `adventureEngine.ts`, `AdventureWorld.tsx`, `GamePane.tsx`, `survivor/scenery.ts`

## 5. IPC 명령 추가·변경

명령 이름은 네 곳이 일치해야 한다. 빌드가 잡지 못하는 항목이 있으므로 함께 수정한다.

1. `src-tauri/src/lib.rs`의 `generate_handler!`
2. `src-tauri/build.rs`의 명령 목록
3. `src-tauri/capabilities/main.json`의 `allow-*`
4. 프런트엔드 호출부

명령을 제거할 때는 `src-tauri/permissions/autogenerated/<명령>.toml`도 지운다. 빌드는 파일을 만들기만 하고 고아 파일을 지우지 않는다.

추가 규칙:

- 명령 함수는 입력 검증과 위임만 하고 로직은 도메인 함수에 둔다.
- DB, keyring, 파일, 외부 프로세스를 쓰는 명령은 `async`로 만들고 `spawn_blocking`을 쓴다. sync 명령은 메인 스레드에서 실행된다.
- 비밀 인자는 함수 첫 줄에서 `Zeroizing`으로 감싼다.
- 이름은 실제 동작대로 짓는다. FTP도 처리하면 `sftp_*`를 쓰지 않는다.
- 응답 타입은 기능당 한 곳에 선언하고 같은 구조를 다시 선언하지 않는다. 이름만 `Status`인 범용 타입을 새로 만들지 않는다.

## 6. Rust

- 락을 쥔 채 콜백, 네트워크, 파일, keyring, KDF, 외부 프로세스를 호출하지 않는다. 값을 복사하고 락을 푼 뒤 호출한다.
- `Store`의 내부 연결을 다른 모듈에서 직접 잠가 SQL을 쓰지 않는다. `storage.rs`에 메서드를 추가한다.
- 새 태스크와 스레드에는 소유자와 종료 경로가 있어야 한다. 무한 루프만 있는 `spawn`을 추가하지 않는다.
- 터미널 동작(ACK, 입력 상한, 크기 검증)을 바꿀 때는 `ssh.rs`, `local.rs`, `podtree.rs`를 함께 확인한다.
- 전송·파일 작업을 바꿀 때는 SFTP와 FTP를 함께 확인하고, 오류 문구도 실제 프로토콜에 맞춘다.
- 오류 문자열 내용으로 제어 흐름을 분기하지 않는다. enum이나 전용 타입을 쓴다.
- 손상된 저장 데이터를 빈 값으로 삼키지 않고 오류로 올린다.
- `[자동]` `cargo fmt`, `cargo clippy -D warnings`.

## 7. 프런트엔드

- 의존 방향은 `app → features → components·lib·themes`다. `components`, `lib`, `themes`는 `features`를 import하지 않는다.
- 기능 간 직접 import를 새로 추가하지 않는다. 공유할 코드는 아래 계층으로 내린다.
- 탭은 `app/workspaceTabs.ts`의 `insertTab`으로 넣는다. 분할 화면은 앞쪽 `paneCapacity`개만 표시한다.
- 새 탭 종류나 연결 종류를 `this.podtree ? … : this.localTarget ? …` 분기로 늘리지 않는다.
- 여러 상태를 인코딩한 문자열(`'discard:id'`) 대신 판별 유니온을 쓴다.
- 순수 로직은 컴포넌트 밖 `.ts`로 빼고 단위 테스트한다.
- 사용자에게 보여줄 프런트엔드 오류는 `lib/ipc.ts`의 `UserError`로 던진다. 일반 `Error`의 메시지는 `errorText`가 표시하지 않는다.
- `localStorage`는 `dachsterm.*` 키만 쓰고, 읽기·쓰기를 try/catch로 감싸며, 읽은 값을 검증한다(`themes/store.ts` 참고).
- 같은 창의 다른 패널에는 `storage` 이벤트가 오지 않는다. 창 내부 동기화에 쓰지 않는다.
- 폴링은 이전 요청이 끝나기 전에 다음 요청을 보내지 않게 한다.
- 빈 `catch`에는 이유를 주석으로 적는다.

## 8. 스타일

- 색상은 테마 토큰만 쓰고, 컴포넌트에서 테마 ID로 분기하지 않는다(roadmap §2.3). 현재 위반 0건을 유지한다.
- 글꼴 크기와 간격도 기초 토큰을 우선 쓴다.
- 새 기능의 CSS는 기능 폴더에 둔다(`tunnels.css`, `transfer.css` 방식). `styles.css`와 `workspace.css`에 추가하지 않는다.
- 다른 파일의 선택자를 뒤에서 덮어쓰지 말고 원본을 수정한다.

## 9. 테스트

- 버그 수정에는 재현 테스트를 함께 넣는다. 환경 때문에 불가능하면 이유를 기록한다.
- 네이티브 검사를 새로 쓸 때 실행 헬퍼 복사를 늘리지 않는다. 공용 헬퍼(review T2) 도입 전까지는 기존 스크립트 수정을 우선한다.
- 새 네이티브 검사는 `verify-windows.ps1 -Native` 또는 npm 스크립트에 연결한다. 문서에만 적힌 명령으로 두지 않는다.
- 테스트 fixture는 제품 타입을 import하고 같은 타입을 다시 선언하지 않는다.
- `[자동]` typecheck, eslint, prettier, vitest, playwright. `npm run typecheck`는 `tests/`도 검사한다(`tsconfig.tests.json`). 단, `scripts/`와 루트 `playwright.config.ts`는 대상이 아니다.

## 10. 줄바꿈

저장소 기준은 LF다. 새 파일과 수정 파일을 LF로 저장하고, 파일 안에 CRLF를 섞지 않는다. `.sh`, `.py`는 `.gitattributes`가 LF를 요구한다.

## 11. Windows·macOS 공통

두 OS 모두 출시 대상이다. 현재 어긋난 부분과 작업 ID는 [macos-readiness](verification/macos-readiness.md)에 있다.

- `#[cfg(windows)]`를 추가하면 다른 OS의 동작도 같은 변경에서 구현한다. 지원하지 않으면 사용자에게 보이는 오류를 반환한다.
- 외부 프로그램을 이름만으로 실행하지 않는다. Finder로 실행한 앱의 `PATH`는 `/usr/bin:/bin:/usr/sbin:/sbin`뿐이라 Homebrew·`/usr/local/bin` 도구를 찾지 못한다. 터미널에서 띄운 `tauri dev`에서는 이 문제가 드러나지 않으므로, 외부 프로그램 실행은 패키지된 앱으로 확인한다.
- `/bin/bash`를 Bash 4 이상으로 가정하지 않는다. macOS 기본은 3.2다.
- `.exe`, `npm.cmd`, `powershell` 같은 이름을 공용 경로에 하드코딩하지 않는다. 제품 코드는 `cfg`로, 스크립트는 `process.platform`으로 분기한다.
- macOS의 로컬 파일 이름은 NFD 한글일 수 있다. 원격 이름을 만들거나 파일 이름을 비교하는 코드는 정규화를 고려한다.
- 단축키는 `ctrlKey || metaKey`로 처리하고, 터미널에 그대로 전달할 `Ctrl+키` 입력과 구분한다.
- 새 Web API는 WKWebView 지원을 확인하고, 없을 때의 동작을 구현한다(`navigator.locks` 사용부 참고). Chromium 전용 CSS에 기능을 의존하지 않는다.
- 글꼴 스택에는 두 OS의 글꼴을 모두 넣는다.
- 네이티브 의존성을 추가할 때는 macOS 빌드를 함께 확인한다.
- macOS CI는 빌드와 자동 테스트만 확인한다. 실기기 항목(Keychain, IME, 파일 대화상자, 설치)의 통과로 기록하지 않는다.
- `[자동]` `macos.yml`의 `verify-macos.sh`.
